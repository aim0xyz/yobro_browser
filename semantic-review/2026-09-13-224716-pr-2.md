# Gate #2 renderer recovery ownership and Qt signal arbitration

The current local Chromium implementation closes all three findings from the prior pass: shell navigation now crosses the session lifecycle boundary, cancelled recovery callbacks are inert, and Qt's untagged load signals are guarded by explicit generations and a targeted harness. Recovery remains on the same page/profile with one automatic attempt, while agent renderer loss fails the active command exactly once without reloading. The legacy StoreOnDisk permission migration remains fail-closed during startup.

Watch for: none; no remaining correctness, security, or lifecycle defect was found in scope.

**Verdict**: APPROVED

## High-level view

`BrowserSession` owns address-bar, Back, Forward, and Reload actions. Profile deactivation makes recovery terminal synchronously, retains the cancelled token, and allows only explicit session navigation or a fresh native `loadStarted` to take later ownership.

`QtBrowserPage` separates requested and signal-bound generations. Retired generations absorb stale false finishes, ambiguity fails as `navigationFailed` on supersession or the five-second watchdog, and every completion requires the exact active token/generation.

The fake controller test, Qt peer, and real process test cover the previously missing interleavings, including immediate reactivation, late state/result, no-`loadStarted` outcomes, stale false ownership, reentrancy, bounded tombstones, and native termination/recovery ordering.

Legacy permissions are reset before the profile reaches a session or page, `AskEveryTime` is installed before use, and the restart test verifies the cleared grant under StoreOnDisk rather than only in memory.

## Cancelled recovery cannot claim later user navigation

`navigateUserTab`, `goBackUserTab`, and `goForwardUserTab` enter `prepareNavigation` before the engine call, and `SpikeWindow` routes the corresponding controls through them. Profile deactivation generation-invalidates queued, loading, and stabilizing recovery; forces `loading=false`; exposes failure; tombstones any active recovery token; and stops the native load.

`onNavigationFinished` checks that tombstone before state forwarding, stability, history, or protocol wake-up. The remaining untagged state guard ignores terminal rollback state and releases only for a loading state from native link navigation; explicit Address, Back, and Forward clear it through `prepareNavigation` before Qt supersedes the prior token.

## Pending and signal-bound generations fail closed

`beginNavigation` installs the newer token/generation before publishing a superseded result, so callback reentrancy cannot erase or trigger the wrong navigation. No-`loadStarted` completion uses only the pending generation, while normal completion, delayed failure, renderer termination, and watchdog callbacks all require an exact token/generation match.

Because Qt does not identify `loadFinished(false)`, superseded and terminated generations form an eight-entry retired queue. A false signal first consumes retired debt; an unresolved ambiguity becomes `navigationFailed` when superseded or when the five-second watchdog expires, rather than being credited to a newer navigation.

## Targeted and native recovery evidence match the required interleavings

The fake scenario performs deactivate → immediate reactivate → late terminal state/result, then proves a direct link can reach stability and session-owned Address/Back/Forward publish fresh terminal state. The Qt peer forces true/false without `loadStarted`, watchdog plus late signal, terminated A → pending B → stale false → true, inverse ambiguity into C, reentrant completion, and more than eight retired generations.

The process-level test requires exactly one `rendererTerminated` result for active load A and exactly one success for recovery B, with native `loadFinished(true)` after `renderProcessTerminated`. Agent read and action crashes return `ok:false`; the action assertion additionally requires a nonempty error, one completion, and no extra request/reload.

## StoreOnDisk migration has no live grant window

Profile construction resets every legacy permission before page creation, pumps Qt's asynchronous persistence work, and then applies `AskEveryTime`. The migration test seeds a real geolocation grant, reopens through the production migration, destroys that profile, and reopens the same storage under StoreOnDisk; the final state must be `Ask`. The temporary event loop runs before the profile escapes its constructor, so no session, page, or permission presenter can observe partially migrated authority.
